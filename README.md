# MiniHotificationService

Регистрация сотрудников и уведомления о назначенных заказах через Telegram.

## Запуск через Docker Compose

Нужен запущенный Docker Desktop с Linux-контейнерами. Python на компьютере не требуется.

1. Скопируйте `.env.example` в `.env`, если файла ещё нет, и укажите `BOT_TOKEN` от BotFather. Существующий `.env` с токеном не перезаписывайте.
2. В корне проекта выполните:

```powershell
docker compose up -d --build
```

Compose запускает PostgreSQL, RabbitMQ, создание таблиц (`db-init`), API, Telegram-бота и обработчик уведомлений. Приложения ждут готовности базы, обработчик и API также ждут RabbitMQ. `db-init` после успешного создания таблиц завершается с кодом 0 — это нормально.

- API и Swagger: [http://localhost:8000/docs](http://localhost:8000/docs).
- RabbitMQ: [http://localhost:15672](http://localhost:15672), логин `guest`, пароль по умолчанию `guest`.
- Состояние контейнеров: `docker compose ps -a`.
- Журналы: `docker compose logs -f api bot consumer db-init`.
- Остановка: `docker compose down`.
- Пересборка после изменения кода: `docker compose up -d --build`.

PostgreSQL находится в контейнере `mini-orders-db`. Данные PostgreSQL и RabbitMQ сохраняются в Docker volumes после остановки и пересоздания контейнеров. Команда `docker compose down -v` удаляет эти данные.

Все приложения в Compose используют PostgreSQL и адреса контейнеров автоматически. Значения `DATABASE_URL` и `RABBITMQ_URL` из `.env` используются только для локального запуска Python. Параметры PostgreSQL и RabbitMQ можно задать переменными из `.env.example`; для паролей используйте символы, безопасные для URL (буквы, цифры, `_`, `-`). На существующих томах PostgreSQL и RabbitMQ изменение переменных не меняет уже созданные учётные данные.

Если раньше база запускалась со старой конфигурацией, проверьте старые учётные данные и сделайте резервную копию перед изменением томов: исправлен путь хранения PostgreSQL 17 на `/var/lib/postgresql/data`. Данные SQLite автоматически в PostgreSQL не переносятся. Создание таблиц не обновляет существующую схему PostgreSQL — для неё нужны миграции.

Не запускайте второй экземпляр бота с тем же токеном одновременно с контейнером `bot`.

## Регистрация

Откройте личный чат с ботом и отправьте `/start`. Бот зарегистрирует Telegram ID и вернёт ID сотрудника. Повторный `/start` возвращает тот же ID. Команда `/profile` показывает профиль, ID сотрудника и Telegram ID.

Альтернатива: `POST /users` через [Swagger UI](http://127.0.0.1:8000/docs):

```json
{"username": "employee", "telegram_id": 9000000001}
```

Ответ содержит `user_id`. Повторная регистрация того же Telegram ID через API возвращает 409. Перед получением сообщений пользователь должен открыть личный чат с ботом и нажать Start.

## Создание заказа и отправка уведомления

Сначала зарегистрируйте создателя и сотрудника через `/start` или `POST /users`. Создайте услугу через `POST /services`:

```json
{"name": "Ремонт", "price": "1500.00"}
```

Создайте заказ через `POST /orders`:

```json
{"service_id": 1, "created_by": 1, "assigned_employee_id": 2}
```

Все три ID должны существовать в базе. `assigned_employee_id` — ID сотрудника из регистрации, а не Telegram ID. Номер заказа, статус `NEW` и время создания назначает сервер. Ответ 201 содержит сохранённый заказ; уведомление автоматически ставится в очередь. Посмотреть актуальные данные можно через `GET /orders/1`.

Повторная отправка существующего заказа — `POST /send`:

```json
{"order_id": 1}
```

Старая схема `/send` с произвольными `id`, `status` и сотрудником больше не принимается. Данные для уведомления берутся из базы. Ответ 202 подтверждает постановку в очередь, а не доставку в Telegram. При недоступности брокера API возвращает 503 с `order_id`: заказ уже сохранён, повторите `/send`, а не `/orders`. При потере подтверждения брокера повторная отправка может привести к повторному уведомлению.

Событие RabbitMQ имеет поля `schema_version`, `event_id`, `event` и `order`. `event` — `order.created` для нового заказа или `order.notification_requested` для повторной отправки. В `order` входят `id`, `service_id`, `service_name`, `status`, `created_by`, `assigned_employee_id`, `created_at`, `updated_at`. Даты передаются в JSON в ISO 8601. Оба события идут в существующую очередь уведомлений по routing key `order.created`. Обработчик перечитывает заказ из базы, чтобы сообщение содержало текущий статус и текущего сотрудника. Старые сообщения прежнего формата несовместимы с новой схемой.

## Изменение статуса в Telegram

Уведомление содержит кнопки доступных статусов:

- Новый → Принят, В работе или Отменён.
- Принят → В работе или Отменён.
- В работе → Выполнен или Отменён.
- Выполнен и Отменён — конечные статусы.

Изменить статус может только Telegram-пользователь, зарегистрированный как назначенный сотрудник. Изменение сохраняется в PostgreSQL, сообщение и кнопки обновляются. Устаревшая кнопка не перезаписывает новый статус. Для актуального сообщения отправьте боту `/order 1` в личном чате. Команда доступна только назначенному сотруднику. Если Telegram не смог обновить сообщение после сохранения, статус остаётся в базе; откройте заказ через `/order`.

API пока предназначен для локального использования без авторизации. Идентификатор `created_by` при создании передаётся клиентом; проверка принадлежности Telegram применяется при работе с заказом через бота.

## Проверка

`docker compose run --rm --no-deps api python -m unittest discover -s tests -v`

Тесты проверяют создание и публикацию заказа, выбор получателя, регистрацию, допустимые переходы статуса, запрет изменений другим сотрудником, устаревшие кнопки и сохранность заказа при ошибке брокера. Telegram и RabbitMQ заменены заглушками, SQLite используется в памяти.

## Структура проекта

- `api/` — приложение FastAPI, маршруты и преобразование ошибок в HTTP-ответы.
- `users/`, `orders/`, `services/` — схемы данных и бизнес-логика; SQL-запросы заказов и пользователей находятся в `repo.py`.
- `messaging/` — подключение RabbitMQ, схема события и публикация уведомлений.
- `consumer/` — один процесс доставки уведомлений; получает собственный экземпляр Telegram Bot.
- `bot/` — команды и кнопки, форматирование карточек, обработка ошибок и сессии базы.
- `database/` — модели, подключение и однократное создание таблиц.
- `common/` — ошибки приложения, независимые от HTTP и Telegram.

Точки входа: `api.main:app`, `python -m bot.main`, `python -m consumer.main`.

В меню Telegram доступны `/start`, `/help`, `/profile`, `/orders`, `/history`, `/order 123`. Списки показывают только заказы текущего сотрудника, по пять на странице. Данные пользователей и названия услуг экранируются при оформлении сообщений. Неизвестная команда предлагает справку; устаревшая кнопка предлагает заново открыть список заказов.
